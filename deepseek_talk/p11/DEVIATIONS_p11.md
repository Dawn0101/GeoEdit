# P11（六方同底座对比）

## P11-D1. 三家基线都是**重实现**，不是作者代码

- `BudEdit` (2609.32841)：官方 README 仍为 `Code - Coming Soon`，**无可运行代码**。
- `ER-Chord` (2610.29248)：论文给的 `github.com/Peizeli1/ER-Chord` **返回 404**（`git clone` 报
  `Repository not found`）。
- `PreciseEdit` (2610.23535)：arXiv 页面**无仓库链接**，全网检索未找到。
- 因此三家均按论文公式在同一底座（官方 `pipeline_chord.py`、同噪声 seed=42、严格 5 NFE）上重实现。
  它们的数字**不代表原作者的最优配置**（尤其 PreciseEdit 的 γ 与 MGA 式的阈值我们只能取论文默认），
  只能作为"同底座同算力"的参考点。这是本报告最重要的限制。

## P11-D2. P10 的 SCAD 实际是 6 次前向，P11 已压回 5 次

- P10 里为了让 SCAD 的掩码 `M_0.75` 来自"未被引导的残差"，先跑了一次 plain `t=0.75` 目标支、再跑
  一次带 hook 的，共 **6 次前向**。
- P11 改为"被引导的那次 `t=0.75` 直接就当作场"（掩码也由它导出），严格 **5 次前向**。
- 因此 P10 与 P11 的 SCAD 数字略有差异：CLIP-E 22.95 → 22.99、PSNR 22.63 → 22.34。
  **论文应以 P11 的 5-NFE 数字为准**；P10 的 6-NFE 结果保留作为"多一次前向"的参考。

## P11-D3. 显存泄漏（0.22 GB/图）

- `PieMetrics.evaluate_many` 在 `torch.no_grad()` 之外被调用，导致每张图保留一份计算图，
  143 图后 OOM。这解释了 P10 dump 两次卡在 143/200。
- 修复：给 `main()` 加 `@torch.no_grad()`，显存恒定 6.73 GB；700 图一次跑完（8 分片）。
- 该 bug 只影响显存，不影响任何数值。

## P11-D4. SCAD-Adap 的 `r` 与 CleanBG 的掩码

- 论文式 `r = ‖m⊙ΔO‖/‖m⊙O_tar‖` 若严格按 `m` 计算需要先有 `M_l`，而 `M_l` 来自被引导的场 —— 循环。
  实现改为在 `t=0.9` 的两次前向里对 **16 个 attn2 层的 ΔO 与 O_tar** 求全局比值（`m=1`），
  不增加任何前向。这是对用户规格的一处偏移，已记录。
- CleanBG 的输出掩码用 `q50/q70`（层内仍 `q40/q65`），未做更多分位扫描。
