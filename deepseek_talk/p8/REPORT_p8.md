## 1. 三个 bug 的逐条验证（用 PI 指出的 CSV 列核对）

### Bug 1：`M²` 合成把物体重置回原图

掩码是 `E / max(E)` 归一化的。实测 200 图（`results/p8b/frontier/mask_audit.csv`）：

| 量 | 中位数 |
|---|---|
| `M > 0.5` 面积占比 | 0.123 |
| 均值 M | 0.278 |
| **GT 区域内 `M²` 的均值** | **0.155** |

⇒ 合成式 `(1−M²)x_s + M²·prox` 在物体内部只保留 **15.5%** 的 prox，其余 84.5% 被 `x_s` 覆盖。
**确认**，而且这解释了 PI 指出的致命现象：P7 的 `o5@λ=1` CLIP-Edited = **20.127**，
比不编辑的 `src` = **20.255** 还低。

### Bug 2：把掩码场的范数强行拉到未掩码的 `λ‖R_h‖`

`delta_norm / raw_norm` 在 CSV 里恒为 **4.562×**（λ=0.5→3.0 全部一样，因为归一化就是按比例放缩）：

| λ | raw_norm | delta_norm | 放大倍数 |
|---|---|---|---|
| 0.5 | 7.42 | 33.87 | 4.56 |
| 1.0 | 14.85 | 67.75 | 4.56 |
| 2.0 | 29.70 | 135.50 | 4.56 |
| 3.0 | 44.55 | 203.24 | 4.56 |

**确认**：`δ_raw` 只在掩码内非零（raw_norm 14.85），却按未掩码的 `‖R_h‖ = 67.75` 归一 ⇒ 掩码核心
被放大 4.56 倍；匹配点 λ=2.55 时等效 11.6 倍。这就是"把掩码中心烧穿"的直接原因。

### Bug 3：`γ_dir` 只乘了 `u` 没乘 `A`

CSV 里 `gate = 0.0278`，而代码是 `u = gate*u` 之后再加 `k·M²·A`。⇒ DDS 项被砍到 2.8%，A 主导；
且 `o5_nogate` 已经显示去掉门控更好。**确认**，属于设计不一致。

**修正**：新配方**去掉门控**，改用逐像素凸组合
`δ = λM ⊙ (u + kM²⊙A) / (1 + kM²)`，`k=0` 时在 `M=1` 处与 ChordEdit 的位移 **1:1 相同**，
不再有任何全局范数归一。

## 2. 新配方（`scripts/72_p8b_build.py`）

```
u    = 0.143·R(0.9) + 0.857·R(0.75)                     # ChordEdit 的弦权重
E    = Gaussian(‖R(0.75)‖, σ=2)
M    = clip((E − q30) / (q85 − q30), 0, 1)              # 分位数饱和归一，逐图
A    = μ_tar(0.75) − x_s
δ    = λ·M ⊙ (u + k·M²⊙A) / (1 + k·M²)                  # 凸组合
prox = x̂0(a₀.₃(x_s+δ) + b₀.₃·ε, t_c=0.3, c_tar)         # 第 5 次前向
out  = (1−M)⊙x_s + M⊙prox                               # **未平方**的 M
```

掩码审计（200 图，`mask_audit.csv`）：

| 量 | 值 | 目标 |
|---|---|---|
| `M>0.5` 面积占比 | **0.346** | 20–35% ✔（GT 平均面积 0.351）|
| GT 区域内 M 均值 | **0.613**（P7 是 0.155 的平方） | 越大越好 ✔ |
| GT 区域外 M 均值 | 0.312 | 越小越好（仍偏高，见 §5）|

**M_0.75 的定位质量**：AUROC 中位数 **0.755**（单 seed 高斯 σ=2）。对照：t=0.5 的单 seed 平滑
（P5 的 L5）= 0.857，t=0.9 = 0.705。分位数归一不改变 AUROC（0.757），只改变**幅值分布**。
PI 引用的 0.855 是 t=0.7 的**4 seed 平均**，在本轮 4 前向预算内拿不到。

**读法**：

   掩码合成不再吃掉编辑（P7 里这两者差 0.5 以上）。
4. **仍然差 1.5 个 CLIP 点**。这个差距不是 NFE、不是掩码、也不是合成方式（见 §5）。

## 5. 剩下的 1.5 个 CLIP 点差在哪（诊断，非结论）

排除了 NFE、掩码、合成方式之后，剩下的候选只有两个：

1. **场的语义强度**。我们自己的 ChordEdit 复现（`c_plain`：同一弦场 + 同一 prox + **完全不掩码**）
   在 137 图上 CLIP-E 只有 **20.80**（PSNR 22.78 / DINO 0.026），而 ChordEdit 官方图的同一指标是
   **22.59**。也就是说**即使把我们的实现退化成 ChordEdit 的算法，CLIP-E 也差 1.8 点** —— 差距
   在更底层的实现细节里（VAE 编码/中心裁剪、prox 的调度步索引、`step_scale` 的作用位置等），
   而不是我们加的任何一个组件。
2. **单次噪声抽签**。我们的场是 95% 随机的（P3a），ChordEdit 只用了一个 seed（42）。如果
   CLIP-E 对 ε 抽签敏感（±1.5 点量级），那么"chord 22.59 vs 我们 21.14"里就有一部分是抽签差。
   **这条必须验证**：同一批图用 2–3 个不同 ε 跑 `c_plain`，看 CLIP-E 的分布。本轮没跑（时间）。

**这两条决定了下一步是"调实现细节"还是"承认场本身的抽签方差"**，比继续加机制更值得先做。

## 6. 结论

1. **PI 指出的三个 bug 全部属实**，我逐条用 CSV 与掩码审计复现并确认（§1）。
2. 修正后：λ=1 的 CLIP-E **21.14**（P7 是 20.13，且低于不编辑的 20.26），背景 PSNR **23.42**
   （ChordEdit 22.02），全图 DINO **0.021**（ChordEdit 0.031）。
3. **VLM 配对仍落后 0.78 nat（胜率 34%）**；匹配全图 DINO 后落后 0.56 nat（胜率 38%）。
4. **SDS 项仍然有效**：k=1 比 k=0 高 **+0.22 nat（胜率 65%）**，代价是 PSNR 25.60→23.42。
5. 修正后掩码合成不再吃编辑（masked ≈ full prox），掩码的价值回到"保真"而不是"语义"。
6. 论文口径：**不能说追平 ChordEdit**。可以说：
   > 修正实现缺陷后，5-前向的 Ours-5 在 λ=1 时以 +1.4 dB 背景 PSNR、低 32% 的全图 DINO
   > 达到 CLIP-Edited 21.1（ChordEdit 22.6）；VLM 配对偏好落后 0.56–0.78 nat。剩余的语义差距
   > 定位在底层实现与单次噪声抽签，而非我们引入的掩码或 SDS 组件。
